Day 59 -- Helm --- Kubernetes Package Manager

Overview

Today I learned Helm, the package manager for Kubernetes. Helm helps
package Kubernetes resources into reusable Charts, install them as
Releases, and manage versions and configuration using values.

Three Core Helm Concepts

Concept                             Meaning

Chart                           A package containing Kubernetes
manifest templates and
configuration

Release                         A specific installed instance of a
Helm chart

Task 1: Install and Verify Helm

Helm was already installed on my Windows machine and was used through
Git Bash.

Verify the installation:

helm version

View Helm environment information:

helm env

These commands confirm that Helm is installed and show its configuration
and environment paths.

Task 2: Add a Repository and Search

I added the Bitnami Helm repository:

helm repo add bitnami https://charts.bitnami.com/bitnami

Update repository information:

helm repo update

Search for nginx:

helm search repo nginx

Search the Bitnami repository:

helm search repo bitnami

Helm repositories provide charts that can be installed into a Kubernetes
cluster.

Task 3: Install a Bitnami Chart

I deployed nginx using the Bitnami chart:

helm install my-nginx bitnami/nginx

Check Kubernetes resources:

kubectl get all

Check Helm releases:

helm list

Check the release status:

helm status my-nginx

View the Kubernetes manifests generated by the chart:

helm get manifest my-nginx

The Bitnami nginx chart created Kubernetes resources without requiring
me to manually write each Deployment and Service manifest.

The release was later observed as:

NAME       NAMESPACE   REVISION   STATUS
my-nginx   default     3          deployed

The installed chart was:

nginx-25.2.1

with application version:

1.31.6

Task 4: Customize Chart Values

Helm charts expose configuration through values.yaml.

View the default nginx chart values:

helm show values bitnami/nginx

A chart can be customized directly using --set.

Example:

helm install nginx-custom bitnami/nginx \
  --set replicaCount=3 \
  --set service.type=NodePort

Nested values use dot notation:

--set service.type=NodePort

Custom Values File

A values file can be used instead of passing many --set options.

Example custom-values.yaml:

replicaCount: 3

service:
  type: NodePort

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi

Install using the values file:

helm install nginx-file bitnami/nginx -f custom-values.yaml

Check the values applied to a release:

helm get values nginx-file

To display all values, including chart defaults:

helm get values nginx-file --all

Important Difference

--set key=value

is useful for individual overrides.

-f custom-values.yaml

is better when multiple configuration values need to be maintained in a
file.

Task 5: Upgrade and Rollback

Helm supports versioned upgrades and rollbacks.

Upgrade the nginx release:

helm upgrade my-nginx bitnami/nginx --set replicaCount=5

Check release history:

helm history my-nginx

Rollback to revision 1:

helm rollback my-nginx 1

Check history again:

helm history my-nginx

A rollback creates a new revision rather than deleting or overwriting
the existing history.

For example, the release history can progress like:

Revision 1  -> Install
Revision 2  -> Upgrade
Revision 3  -> Rollback

This makes Helm useful for application version management and recovery.

Task 6: Create a Custom Helm Chart

Create a chart scaffold:

helm create my-app

The resulting chart contains files and directories such as:

my-app/
├── Chart.yaml
├── values.yaml
├── charts/
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── serviceaccount.yaml
    └── tests/

Important Files

Chart.yaml

Contains chart metadata such as the chart name and version.

values.yaml

Contains default configuration values used by the templates.

templates/

Contains Kubernetes manifest templates.

Go Template Syntax

Helm templates use Go template syntax.

Examples:

{{ .Values.replicaCount }}

Gets a value from values.yaml.

{{ .Chart.Name }}

Gets the chart name.

{{ .Release.Name }}

Gets the name of the Helm release.

This allows one Kubernetes template to generate different manifests
based on configuration.

Customizing my-app

I changed the chart values to use three replicas:

replicaCount: 3

The nginx image was configured as:

image:
  repository: nginx
  pullPolicy: IfNotPresent
  tag: "1.25"

The important point is that image must be a YAML object when the chart
template expects fields such as repository, pullPolicy, and tag.

YAML Error and Fix

Initially, values.yaml contained:

image: nginx:1.25
  repository: nginx

This produced:

yaml: line 10: mapping values are not allowed in this context

The problem was that image was defined as a string and then nested
properties were placed underneath it.

I corrected it to:

image:
  repository: nginx
  pullPolicy: IfNotPresent
  tag: "1.25"

After correcting the YAML:

helm lint .

returned:

1 chart(s) linted, 0 chart(s) failed

The Chart.yaml: icon is recommended message was informational and did
not cause the lint failure.

helm lint

helm lint validates the chart structure and checks for common chart
errors.

When I was inside the my-app directory, this command was correct:

helm lint .

When I was one directory above it, this command was correct:

helm lint my-app

Initially I ran:

helm lint my-app

while already inside the my-app directory.

Helm then searched for:

my-app/my-app/Chart.yaml

and failed because that path did not exist.

The fix was:

helm lint .

Preview Templates Without Installing

From the parent directory:

helm template my-release ./my-app

This renders the Kubernetes manifests locally without installing the
release.

The rendered Deployment showed:

replicas: 3

and:

image: "nginx:1.25"

The rendered Service used:

type: ClusterIP

This is useful for debugging Helm templates before deploying them.

Install the Custom Chart

Install the chart:

helm install my-release ./my-app

The release was successfully installed:

NAME: my-release
NAMESPACE: default
STATUS: deployed
REVISION: 1

The resulting Deployment initially had three replicas.

Verification:

kubectl get pods

The three application replicas were running.

Upgrade the Custom Chart

The release was upgraded from three replicas to five.

Correct command:

helm upgrade my-release ./my-app --set replicaCount=5

I initially used:

helm upgrade my-release ./my-app -set replicaCount=5

which failed because -set is not the correct option.

The correct syntax is:

--set

After the successful upgrade, Helm reported:

Release "my-release" has been upgraded.
REVISION: 2

The Kubernetes pods showed five running my-release-my-app replicas.

Task 7: Clean Up

List all Helm releases:

helm list -A

The releases created during the exercise included:

my-nginx
my-release

I initially tried to uninstall using the chart name:

helm uninstall my-app

This failed because my-app was the chart name, not the release
name.

The actual release was:

my-release

The correct cleanup commands were:

helm uninstall my-nginx
helm uninstall my-release

After cleanup:

helm list -A

returned no deployed releases.

Keep Release History

If release history needs to be retained for auditing:

helm uninstall my-nginx --keep-history

Then history can be inspected using:

helm list --uninstalled
helm history my-nginx

Key Learnings

Chart = reusable Kubernetes package.

Release = installed instance of a chart.

Repository = collection of charts.

--set is useful for quick configuration overrides.

-f values.yaml is useful for managing multiple configuration
values.

helm template allows manifests to be reviewed before installation.

helm lint catches chart and YAML problems before deployment.

helm upgrade creates a new release revision.

helm rollback creates another revision while restoring an earlier
configuration.

The chart name and release name are different concepts.

YAML indentation and structure are critical for Helm values.

Helm can replace large amounts of manually maintained Kubernetes
YAML with reusable templates and values.

Conclusion

Day 59 introduced Helm as the Kubernetes package manager. I deployed a
Bitnami nginx chart, customized chart values, performed upgrades and
rollbacks, created my own Helm chart, used Go templating, validated the
chart with helm lint, rendered manifests with helm template, and

templates, configuration values, and release history, making
Kubernetes deployments easier to package, customize, upgrade, and roll
back.
